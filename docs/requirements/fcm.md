# FCM Requirements

## 목적

유저당 활성 로그인 세션 1개 정책에서 현재 활성 기기의 FCM Token을 관리하고, 사용자 대상 푸시 알림 발송 동작을 정의한다.

FCM Token은 인증 세션과 연결되어야 하며, 세션이 교체되거나 무효화될 때 함께 정리될 수 있어야 한다.

## 기능 요구사항

- 사용자는 로그인 후 현재 활성 세션에 대한 FCM Token을 등록할 수 있어야 한다.
- FCM Token은 현재 `ACTIVE` 세션과 연결되어야 한다.
- 한 사용자에게 동시에 유효한 FCM Token은 현재 `ACTIVE` 세션의 토큰 1개를 기준으로 한다.
- 같은 사용자가 새 기기에서 재로그인하면 기존 세션의 FCM Token은 무효화되어야 한다.
- 현재 세션에서 FCM Token을 다시 등록하면 기존 FCM Token은 새 값으로 갱신되어야 한다.
- 로그아웃 시 현재 세션에 연결된 FCM Token은 무효화되어야 한다.
- 회원 탈퇴 또는 계정 비활성화 시 해당 사용자의 모든 세션과 FCM Token은 무효화되어야 한다.
- 사용자 대상 알림은 현재 `ACTIVE` 세션에 연결된 FCM Token으로만 발송되어야 한다.
- 유효하지 않은 FCM Token이 확인되면 서버는 해당 토큰을 정리할 수 있어야 한다.

## 인증/세션 연동 요구사항

- FCM Token 등록 API는 인증된 사용자만 호출할 수 있어야 한다.
- FCM Token 등록 시 Access Token의 `sessionId`가 `ACTIVE` 상태인지 확인해야 한다.
- `REVOKED` 세션에서는 FCM Token을 등록하거나 삭제할 수 없어야 한다.
- FCM Token 삭제는 현재 요청의 `sessionId`와 연결된 토큰을 대상으로 해야 한다.
- 사용자 ID만으로 임의 세션의 FCM Token을 삭제해서는 안 된다.

## 비기능 요구사항

- FCM Token 저장/갱신은 세션 상태와 일관성을 유지하도록 트랜잭션 범위에서 처리되어야 한다.
- 알림 발송 실패는 핵심 도메인 흐름을 실패시키지 않고 로그로 추적 가능해야 한다.
- 유효하지 않은 FCM Token은 반복 발송을 줄이기 위해 정리되어야 한다.
- 푸시 알림에는 민감한 개인정보를 포함하지 않아야 한다.
- FCM Token은 필요한 알림 발송 목적 외로 사용되어서는 안 된다.

## 예외/제약사항

- 빈 값 또는 유효하지 않은 FCM Token은 등록할 수 없다.
- 같은 FCM Token이 다른 사용자 또는 다른 세션에 등록되는 경우 기존 바인딩은 정리되어야 한다.
- 알림 전송 실패가 학습 세션 종료 같은 핵심 도메인 동작을 실패시키면 안 된다.
- FCM Token이 없거나 유효하지 않은 경우 알림 발송은 건너뛸 수 있어야 한다.
- 앱 삭제/재설치로 기존 FCM Token이 유실되어도 사용자는 재로그인 후 새 FCM Token을 등록할 수 있어야 한다.

## 관련 API

- `POST /api/v1/fcm/token`: 현재 활성 세션의 FCM Token 등록 또는 갱신
- `DELETE /api/v1/fcm/token`: 현재 활성 세션의 FCM Token 삭제

## 검증 시나리오

- 로그인 후 FCM Token을 등록하면 현재 `ACTIVE` 세션과 토큰이 연결된다.
- 같은 계정으로 새 기기에서 재로그인하면 기존 세션의 FCM Token은 무효화되고 새 세션의 FCM Token만 유효해진다.
- 기존 기기의 세션이 `REVOKED`된 뒤 FCM Token 등록을 시도하면 실패한다.
- 로그아웃하면 현재 세션의 FCM Token이 삭제되고 해당 토큰으로 알림이 발송되지 않는다.
- 사용자 대상 알림은 현재 `ACTIVE` 세션의 FCM Token으로만 발송된다.
- 회원 탈퇴 시 해당 사용자의 모든 FCM Token이 삭제된다.
- 유효하지 않은 FCM Token으로 전송 실패가 발생하면 서버는 해당 토큰을 정리할 수 있다.
